# ADR-0002：一致性优先于随机性，SHA-256 逐字段派生

- **状态**：已接受
- **日期**：2025-09
- **决策者**：维护者
- **相关**：[ARCHITECTURE.md](../ARCHITECTURE.md) §3.1、`src/proteus/fingerprint/derive.py`

## 背景

设计指纹派生时有两个直觉上相反的选项：

**A. 随机化**：每次启动生成一套全新的随机指纹，尽可能"不像别人"。
**B. 稳定 + 自洽**：一个 Profile 绑定一个 seed，指纹永久固定，且各字段互相一致。

同时还要决定**用什么随机源**：

1. `random.Random(seed)` —— 方便，但 CPython 未承诺跨版本一致
2. `uuid.uuid5` —— 稳定，但只能取 128 bit 且不便于逐字段
3. `hashlib.sha256(f"{seed}:{field}")` —— 稳定、逐字段独立、可手算

## 决策

**采用 B + 方案 3。**

- 指纹由 `(seed, geo)` 确定性派生，同输入永远同输出
- 每个字段独立计算：`idx = sha256(f"{seed}:{field}")[:8] mod len(choices)`
- 时区、locale、语言**不由 seed 决定**，由代理出口 IP 的地理位置强制决定
- 派生结果必须通过一致性规则集，`fatal` 级违规直接拒绝启动

## 理由

### 1. 随机化会主动制造矛盾

这是最反直觉但最重要的一点。字段之间是有联合约束的：OS 决定字体集、决定 WebGL vendor、决定合理的 DPR 范围、决定 UA 格式。独立随机化等于在几十个维度上同时投骰子，**必然**产生"Windows UA + Apple GPU"这类组合。

随机化让指纹"更稀有"，但稀有本身不是优势——**稀有 = 可追踪**。一个全世界只有你有这个指纹的浏览器，比一个和十万台真实 Windows 机器长得一样的浏览器更容易被记住。

所以正确目标不是"独特"，是"**落在一个真实设备的合理分布内，且内部一致**"。

### 2. 稳定性是产品需求

- 用户今天登录的店铺，明天用同一个 Profile 打开，必须还是"同一台设备"。指纹漂移等于换机器，风控直接触发。
- 平台侧的设备信任是**累积**的。稳定的指纹在积累信用，随机的指纹在每次重置。

### 3. 逐字段独立，避免升级漂移

如果用 `random.Random(seed)` 顺序取数：

```python
rng = random.Random(seed)
os = rng.choice(OS)          # 取一次
ua = rng.choice(UA)          # 取一次
# 后来新增了一个字段插在中间……
os = rng.choice(OS)
new_field = rng.choice(X)    # ← 这一个插入让后面所有字段全部错位
ua = rng.choice(UA)          # 值变了！
```

结果是**升级一次，所有存量 Profile 指纹全变**。这是灾难性的产品缺陷。

逐字段哈希彻底消除这个问题：`sha256(f"{seed}:{field}")` 只取决于该字段名，新增字段不影响任何已有字段。

### 4. 跨版本、跨平台可复现

`random.Random` 的 Mersenne Twister 实现在 CPython 版本间虽大体稳定但**无正式保证**，且 `choice` 的实现细节（如采样算法）曾变更。SHA-256 是标准算法，结果由定义保证。

这决定了 Profile 可以在 Windows 上创建、Linux 服务器上运行，指纹完全一致。

### 5. 可审计

用户问"为什么我这个环境是 2560×1440？"，可以手算出来：

```python
int.from_bytes(sha256(b"20250922:screen").digest()[:8], "big") % len(SCREENS)
```

不需要复现任何隐藏状态。对一个安全相关的工具，"我能验证它"比"相信我"重要得多。

### 6. geo 必须是硬约束

时区、语言、locale 如果随机，就会出现"德国 IP + UTC+8"，这是**最容易被抓的破绽**，且完全无谓。代理决定了你在哪，指纹就必须承认你在哪。

所以这四个字段被明确排除在 seed 派生之外，由 `GeoProfile` 强制注入，且 `check()` 会校验它们的一致性。

## 后果

**正面**
- 指纹跨版本、跨平台稳定
- 新增字段不破坏存量 Profile
- 派生过程可手算、可审计、可测试
- 零第三方依赖（`hashlib` 是标准库）

**负面**
- 同一 seed 产出的指纹是"可预测的"——知道算法的人能算出任意 seed 的指纹。**这在威胁模型里不是问题**：检测方不知道也不关心你的 seed，它只看浏览器实际暴露什么。
- 指纹分布依赖内置的候选表质量。候选表做得好不好，直接决定"看起来像不像真实设备"。这转移到 M0 遗留项与后续的数据工作。
- 无法通过"重新随机"来碰运气绕过某个检测——这是设计意图，不是缺陷。

## 备选方案与被否理由

| 方案 | 否掉理由 |
|---|---|
| 每次启动随机指纹 | 必然字段矛盾；破坏设备信任累积 |
| `random.Random(seed)` 顺序取数 | 插入字段导致全量漂移；跨版本无保证 |
| `uuid.uuid5` | 逐字段需拼接命名空间，可读性差，无实质优势 |
| 从真实设备库随机抽样 | 方向正确，但需要设备库；可作为候选表的数据来源（后续） |

## 复核条件

1. 需要支持"每会话指纹"的特定场景（如纯研究用途）时，作为**独立模式**添加，不改变默认语义
2. 候选表升级导致指纹分布变化时，必须通过**版本化**处理：`meta.json` 记录派生版本号，存量 Profile 锁定旧版本表
